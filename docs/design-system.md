# TypeLoop design system

TypeLoopのUIは、タイピング中の集中を守り、結果を一目で理解でき、長時間でも疲れにくいことを最優先にする。既定の`noir`は白黒に近い静かな表現、`modern`は同じ構造のライト表現、`classic`は互換性を保つ従来表現である。

## 原則

1. **集中が主役。** 装飾は情報階層を助ける場合だけ使う。プレイ中は問題文、入力位置、残り時間の順に視線が流れるようにする。
2. **色ではなく役割で設計する。** コンポーネントは`--canvas`、`--surface`、`--content-*`、`--control-*`などのセマンティックトークンを使う。パレット名を直接使うのは既存スタイルの段階的移行に限る。
3. **モノクロでも意味が伝わる。** 選択、エラー、成功は色だけに依存せず、枠線、形、文言、状態属性を組み合わせる。ステータス色は意味のあるフィードバックに予約する。
4. **一貫した深度。** `canvas → surface → raised/inverse`の少数段階で奥行きを作る。強いグラデーションや過剰な影を重ねない。
5. **即時性を壊さない。** テーマ変更でReactツリーを分岐させない。ルート属性とCSSトークンで切り替え、入力処理やセッション状態に再描画コストを持ち込まない。

## トークンの責任

- `--canvas`: ページ全体の背景
- `--surface`, `--surface-inverse`: カードや反転面
- `--content-primary`, `--content-strong`: 本文と見出し
- `--content-secondary`, `--content-muted`: 補足情報
- `--control-primary`, `--control-on-primary`: 主要操作とその前景
- `--focus-accent`: キーボードフォーカスと選択状態
- `--accent-soft`: 控えめな強調。通常本文には使わない

生の色、影、角丸、余白、モーション、レイアウト閾値は`app/styles/themes.css`の`@tokens`レジストリだけに置く。コンポーネントやTSXへ値を直書きしない。ブラウザmetadataだけが必要とする色は、生成スクリプトがこのCSSから`browser-theme-colors.generated.json`へ導出し、`check:generated`が差分を拒否する。`npm run check:tokens`がそれ以外の境界を検証する。

画面固有のselectorは画面と同じディレクトリのCSS Moduleが所有する。`globals.css`にはdocument基盤と複数画面で意図的に共有するcontrolだけを置き、新規画面の都合でglobal selectorを増やさない。既存global styleは、その画面を変更するPRで視覚回帰を保ちながら段階移行する。

## テーマ要件

- 主要な本文・操作・反転面は全テーマでWCAG AA（4.5:1以上）を満たす。
- `color-scheme`をテーマに合わせ、フォーム部品やブラウザUIも不自然に反転させない。
- テーマは静的HTMLの安全な既定値と`<head>`の検証済みpre-paint bootstrapで初期描画され、フラッシュを起こさない。
- 新しいテーマは許可リスト、設定ラベル、プレビュー、コントラストテスト、E2E永続化テストを同時に追加する。
- `noir`では純黒一色にせず、近接したニュートラル面で階層を作る。白は主要操作や最重要情報に限定する。

## インタラクションと性能

- 主要操作のタップ領域は44px以上。
- 情報を伝える文字は11px未満にしない。最小サイズは`--font-micro`、通常の補足は`--font-caption`を使い、画面固有の極小文字を作らない。
- フォーカス表示を消さない。フォーカス順は見た目の順序と一致させる。
- ホームでは「モード選択 → 開始 → 進捗 → 参考資料」を操作優先度とDOM順の両方で維持する。ヘッダー先頭のキーボードショートカットから主要操作へ直接移動できるようにする。
- モーションは160ms前後を基準とし、`reduced`設定では実質停止する。
- テーマ切替のための依存パッケージ、画像、ランタイム通信を追加しない。
- `backdrop-filter`は補助表現とし、読める背景色を必ず併記する。

## レスポンシブ作業面

- 画面サイズは`viewport → themes.cssの流動トークン → PageShell → 画面内レイアウト`の順に解決する。各画面で外側の最大幅、中央寄せ、viewport余白を重複定義しない。
- `PageShell`の幅は用途で選ぶ。`wide`は一覧、`default`はホーム、`reading`は結果・履歴、`assessment`は試験の導入・結果、`session`/`game`は集中作業、`compact`は設定に使う。新しい幅を数値都合だけで追加しない。
- 外側余白は論理プロパティとsafe-areaを使い、幅は`clamp()`で連続的に、上下密度は`dvh`で高さにも追従させる。端末名だけを理由に固定値へ分岐しない。
- 標準的なPC表示ではヘッダー、主要操作、進捗、参考資料、フッターをファーストビュー内に収める。高さが足りない端末では情報を隠さず、縦スクロールへ安全に切り替える。
- PCでは主要操作と補助情報の2領域、900px以下では同じDOM順の1列構成とする。CSSによる視覚順の入れ替えは行わない。
- Grid/Flexの各子要素には縮小余地を持たせ、操作ラベルは省略記号で隠さず折り返す。キーボード表記や矢印などの固定要素だけを縮めない。
- 320px幅、電話横向き、タブレット、標準ノートPC、デスクトップをレイアウト同値クラスとして検証する。全クラスでページ全体の横スクロール、操作要素の内容切れ、44px未満のタップ領域を許容しない。多数の選択肢を保つ局所的な横スクロールレールは、操作可能であることを検証した場合だけ使用できる。
- 主要レイアウトは絶対配置に依存させず、幅・高さ・縦横比の変化に対してGrid/Flexと`clamp()`で連続的に追従させる。

## レビュー手順

変更時は320×568、390×844、667×375、768×1024、1280×720、1440×900、1920×1080をレイアウト同値クラスとして扱う。compact phoneとdesktopでは全画面、その他は全`PageShell`役割を代表する画面を確認する。キーボード操作、横スクロール、内容切れ、コントラスト、テーマ再読み込み、コンソールエラーを検証し、最後に`npm run check:ci`を通す。

主要4画面のnoir表現はChromiumのプラットフォーム別画像を基準に比較する。画像更新は意図したデザイン変更と同じPRだけで行い、差分をレビューする。OG画像は1200×630かつ150KB以下、インストール用アイコンは宣言サイズと実寸を一致させる。
